Memory Requests
===============

Memory request records are immutable event payloads used to command a
``QuantumMemory`` component. They describe the operation to attempt; they do not
mutate qstate or memory positions by themselves.

Pass request objects as ``Event.payload_ref`` values to public memory actions.
The memory checks live position state at event time, performs the operation when
possible, and emits a report when that operation produces one.

Choosing The Right Request
--------------------------

.. list-table::
   :header-rows: 1
   :widths: 32 32 36

   * - Need
     - Request
     - Important behavior
   * - Store a photon signal
     - ``MemoryAbsorbRequest``
     - ``position=None`` lets memory choose the first available ready slot.
   * - Emit a stored qubit as a photon
     - ``MemoryEmitRequest``
     - Requires an occupied position and a connected output port on success.
   * - Apply a qstate operator
     - ``MemoryApplyOperatorRequest``
     - Ordered ``positions`` become ordered qstate targets.
   * - Measure memory contents
     - ``MemoryMeasureRequest``
     - Can be destructive or non-destructive.
   * - Remove one occupied position
     - ``MemoryDiscardRequest``
     - Discards qstate and clears the position into recovery.
   * - Lifetime cleanup with a token guard
     - ``MemoryExpireRequest``
     - Usually scheduled internally after absorb.
   * - Change position metadata
     - ``MemoryUpdateMetaRequest``
     - Classical-only; does not touch qstate or timing fields.

Runtime Checks
--------------

``MEMORY_ABSORB`` may also receive a quantum ``PortDelivery`` carrying a
``Signal``. In that path, ``QuantumMemory`` creates an internal absorb request
with an autogenerated request id, ``position=None``, and connection metadata.

``MemoryApplyOperatorRequest`` and ``MemoryMeasureRequest`` use ordered
``positions`` tuples. The order is preserved when resolving qstate targets.

``MemoryUpdateMetaRequest`` changes classical metadata on one occupied position.
Use ``expected_occupancy_token`` when delayed protocol decisions must not update
a newer occupancy of the same physical slot.

``MemoryExpireRequest`` is normally scheduled by ``QuantumMemory`` after a
successful absorb when ``storage_lifetime_ticks`` is configured. The occupancy
token lets stale expiry events be ignored.

Construction Versus Runtime Checks
----------------------------------

Request constructors validate structure early: ids are non-empty, positions are
non-negative, multi-position operations use non-empty unique tuples, bool fields
are real bools, and metadata has the package metadata shape.

Construction-time validation does not mean the event will succeed. Runtime
success still depends on the target memory id, current position status, recovery
time, qstate target validity, output connections, and delayed-operation tokens.

User code should schedule only public memory actions and request records.
Private completion payloads are implementation details of delayed
``QuantumMemory`` operations.
